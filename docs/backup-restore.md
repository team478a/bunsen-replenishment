# バックアップと復元（第5段階）

バックアップは取込原本・計算・手修正・発行スナップショットを含むSQLite履歴と、アプリのreportsフォルダーのファイルを保存する。元CSVフォルダー、アプリの未保存画面、ブラウザー等で別フォルダーに保存したPDFは含まない。原本CSVはDB履歴内に保存されている。

## 保存と検証

管理画面でZIPの保存先を指定する。既存ZIPと現在のデータフォルダー内への保存は拒否する。SQLiteバックアップAPIでDBの一貫したスナップショットを取得する。帳票ファイルは保存時点のコピーで、別アプリ画面からの同時出力との一括トランザクションではない。正本はDBの発行履歴で、帳票は履歴から再出力できる。

コミット済みWAL更新も含め、単体のDBファイルへ保存する。未完了の更新がある接続は拒否し、DBコピーは30秒を超えたら中断を判定する。ロックや容量不足等では保存完了を表示しない。通常の接続設定は処理後に戻す。

ZIPはformat=bunsen-backup、version=1のmanifest.json、history.db、任意のreports配下ファイルを含む。マニフェストに日時、件数、直近発行番号、各ファイルのサイズとSHA-256を保存する。チェックは破損検出であり、電子署名による真正性証明ではない。現在の技術上限は1ファイル1GiB、全体2GiB、10,000エントリ、マニフェスト1MiB。上限を超えたら保存方式を見直す。

パス逸脱・重複・シンボリックリンク・Windowsで危険なファイル名を拒否し、SQLite整合性、対応するテーブル、JSON、番号／改訂、原本ハッシュ、発行イベントとの一致を確認する。過去履歴の業務値を現在の確認済みデータとして再認定する検証ではない。

## 復元と閲覧

まずZIPを選んで検証し、件数・直近発行番号・作成日時を確認する。次に復元先の親フォルダーを選ぶ。ZIPが変わっていれば停止する。検証後に一意の新規フォルダーを作り、既存データは上書きしない。復元先にはrestore-info.jsonを付け、アプリはその履歴DBをSQLiteの読み取り専用モードで開く。

復元履歴では履歴閲覧・帳票再出力・再バックアップができる。CSV取込・計算の保存・仮指示再開・編集保存・新たな帳票発行は停止する。古い発行番号を再使用しないためである。「通常データへ戻る」で元のデータフォルダーへ戻る。切替時に未発行の画面編集は失われる。復元前に必要な編集を仮指示として保存する。

再出力には「復元履歴の参考帳票・実出荷に使用しない」を付け、view-outputに保存する。元のreports内ファイルは保持し、それらも実出荷には使用しない。アプリが示す最新改訂は復元した履歴内だけの照合であり、現在の現場の最新版とは限らない。通常DBが存在しないPCでは、空の通常DBを自動作成して運用へ戻すことはしない。

この段階では、現行DBへの差戻し・履歴の合成・本番書込モードへの昇格は提供しない。PC故障時等の本番復帰には、バックアップ以降の出荷・改訂・現物在庫を責任者が照合し、番号と履歴の扱いを決める必要がある。restore-info.jsonの削除やDBの手動置換で制限を回避しない。

## CLI（GUI起動できない場合も使用可能）

```powershell
python -m bunsen.backup create "C:\path\BunsenReplenishment" "D:\backup\bunsen.zip"
python -m bunsen.backup inspect "D:\backup\bunsen.zip"
python -m bunsen.backup restore "D:\backup\bunsen.zip" "C:\recovery"
python -m bunsen --data-dir "C:\recovery\restored-..."
```

CLI復元も新規フォルダー・閲覧専用で、同じ検証を行う。バックアップには業務データが含まれるので、リポジトリへコミットせず、ブンセン側で保存先・保管期間・アクセス・別媒体コピーを管理する。実環境での障害復旧受入試験は別途必要。

Windows試用ZIPではPythonコマンドの代わりに`BunsenTools.exe backup create / inspect / restore`を使える。復元履歴は`BunsenReplenishment.exe --data-dir 復元フォルダー`でも閲覧専用で開く。詳細は`windows-distribution.md`を参照。
