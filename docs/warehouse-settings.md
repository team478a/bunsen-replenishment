# 倉庫別補充条件への改修（0.7.6）

## 調査と変更方針

0.7.5までの計算エンジンは、倉庫・商品別の計算行にある配送リードタイムから到着日と需要対象期間を算出していた。一方、0.7.3で商品別設定を簡素化した際、画面と保存条件を神戸・杉戸共通にし、生成する計算行へ同じ日数を渡していた。この画面・保存・適用部分を修正し、既存の倉庫別計算エンジンと帳票出力を再利用する。

商品別設定・条件CSV・複雑な対象選択は戻さない。画面にはKOBE（ムロオ神戸）とSUGITO（ムロオ杉戸）を並べ、両倉庫の条件を別々に入力する。倉庫番号は保存条件のキーと生成する計算行にも含める。

## 現行仕様

- 補充間隔、到着までの日数、安全在庫日数、補充対象日数を各倉庫に保存する。各倉庫内では全商品共通。
- 到着日＝出荷日＋その倉庫の到着までの日数（暦日）。到着前の需要、安全在庫、対象期間、入荷前欠品警告に各倉庫の条件を使う。
- JAN・倉庫別物理PLで切り上げる既存ルールと、14日配送計画の便容量条件を維持する。
- 片倉庫の欠損・不正値を他倉庫の数値や0で補完しない。保存を全件停止し、倉庫名・項目を表示する。両倉庫の設定がなければ新しい画面での計算を止める。
- 担当者・理由・保存時刻・版・変更前後を保持する。変更後は両倉庫の結果を無効化し、再取込・再計算を要求する。以前の条件による未確定結果・配送計画を正式確定できない。
- 見出しのKOBE/SUGITOはアプリ内の倉庫番号。外部予測CSVの倉庫番号は、担当者が予測取込時に保存した対応を表示するだけで推定しない。外部番号の対応管理を補充条件に重複して持たせない。
- 業務で確認された具体的な日数をこの改修で勝手に初期値へ設定しない。デモの神戸0日・杉戸2日は架空の検証条件。

## 保存と旧履歴互換

イベントは既存の `common_settings_change` を利用する。新しい `after` は `KOBE` / `SUGITO` をキーに持ち、それぞれに4項目を保存する。既存の単一4項目のイベント・原本CSV・発行指示は当時の意味のまま保持する。

内部証跡 `common-settings.csv` は新形式で `warehouse,revision,cycle_days,lead_days,safety_days,coverage_days,operator,reason,saved_at` の2行。両倉庫を1行ずつ、同じ版・担当者・理由・保存日時で保存する。旧形式の1行も原本互換読取できる。これは利用者が作成する入力CSVではない。

取込時に保存条件から倉庫別の `requirements.csv` を生成し、証跡と計算行の一致を検証する。計算根拠・発行原本・バックアップに当時の条件を保存する。正式Excel/PDFの到着日と、14日計画の出荷日・到着日の差は倉庫別リードタイムに一致する。

以前の共通条件は画面の説明欄に表示し、履歴にも残す。新しい倉庫別入力欄には自動適用せず、両倉庫の条件を確認保存するまで新規の画面取込を停止する。旧APIの共通条件読取は履歴互換用として維持する。過去の指示は以前の到着日・数量で再出力できる。

## 検証計画と実装範囲

1. 倉庫別保存と証跡の追加、旧形式の互換保持。
2. 画面を両倉庫の入力欄に変更し、新規画面で旧共通条件の自動適用を停止。
3. 片倉庫の変更が他倉庫の計算数量・到着日を変えないこと、異なる到着日と入荷前欠品警告、14日計画、Excel/PDFを架空データで検証。
4. 欠損・不正値・倉庫重複・条件と証跡の不一致、旧履歴保持、変更後の確定停止、バックアップ復元、閲覧専用の回帰試験。
5. 全自動テスト、固定日付デモ、Windows配布版self-test（倉庫別経路を追加）を実行する。

実データ・認証情報はコミットしない。旧データの削除・自動移行は行わない。現場の実際の日数・外部倉庫番号の確認と手操作受入は別途必要。
