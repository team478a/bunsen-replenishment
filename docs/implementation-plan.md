# 段階的な実装計画

1. 方針・業務仕様・仮CSV契約・未確定事項を先に作成する（この6文書）。
2. Python標準ライブラリでCSV取込・厳格検証、商品別換算、リードタイム・輸送中・予測を使う計算を作る。
3. 共有現物ロット在庫・期限・専用車両重量の検証、手修正、当日朝ゲートを実装する。
4. 日本語Tkinter画面、SQLite履歴、改訂採番、倉庫別印刷HTMLとPDF印刷導線を実装する。
5. 架空の前日／朝サンプルで全フローをデモ化。二重割当、欠損と0、換算、期限、容量、当日朝未確認、変更後再検証を自動テストする。
6. 実装・検証・制限をPRでレビューする。実データ接続・業務承認完了とは扱わない。

後続：本番CSV整備と責任者承認、現場受入試験、複数ロット・混載／容積・カレンダー、追加出荷と実績管理、署名付きexe配布、期間拡張、KPI集計。追加要件ごとにデータ契約と検証を拡張する。

## 第2段階：発行前検証・履歴の安全性強化

実CSVと業務設定の承認を待つ間、次の不具合予防を実装する。配分・期限・安全在庫などの業務設定は追加確定しない。

- 到着日までの在庫を日別に追い、後日の輸送中数量によって前日の不足警告が消えないようにする。予測残高を確定在庫と区別し、入庫日の時刻順は未確認として表示する。補充数量の既存集計式は維持する。
- 正式発行で計算開始時点の改訂を照合する。別画面で同日正式指示が発行されていたら停止し、再計算・再確認を求める。同じ画面からの発行後は再計算を必要とする。
- 帳票再出力時にDBの現行改訂を照合し、旧版には「出荷に使用しない」と明示する。取込・計算・発行の原本履歴は変更しない。既に配布された紙・PDFの回収は従来どおり運用側の責任。
- 未対応CSVを黙認しない。注文・製造予定など、契約外のCSVが同じフォルダーにあればファイル名を示して停止する。
- 受入条件：日別不足の再現、2接続からの競合停止、旧版再出力表示、既存DBとの互換性、未対応CSV拒否、既存全テストと固定日付デモ、Windows CIの成功。

## 第3段階：担当者による複数ロット分割

- 倉庫・商品ごとの計算明細を維持し、その中にロット別のP数量を保持する。自動ロット選択・自動配分は行わない。
- 専用画面で指示総量Pと複数ロットの数量を入力する。朝在庫・賞味期限・他倉庫を含む既割当を見ながら追加・変更・削除できる。
- 正式発行にはロット別数量の合計と指示総量の一致を要求し、各ロットを甲単位で検証する。ロット別の倉庫横断合算と、商品全体の専用車両重量も検証する。
- 不完全な割当は仮指示として保持できるが、不一致・未割当を画面と帳票に表示し、正式発行は止める。
- 変更後は確認を解除し全検証をやり直す。帳票はロットごとの数量・単位・期限・確認日時を記載する。
- CSV列とDBテーブルは維持する。既存の単一ロット履歴を読み込み・再出力できるようにする。
- 受入条件：複数ロットでの正式発行、合計不一致、別倉庫を含む同ロット超過、混在する期限違反、ロット別甲端数、合計積載超過、編集後の再検証、旧帳票互換、全テスト・固定日付デモ・Windows CIの成功。

## 第4段階：仮指示の再開と朝データ照合

- アプリ再起動後、履歴から最新の仮指示を再開する。保存した取込原本から再計算し、指示数量・単一／複数ロットの手修正を復元する。確定操作・担当者名・検証済み状態は復元しない。
- 再開中のCSV再取込・再計算では手修正を保持し、最新の在庫・予測・設定で根拠と不足を再検証する。取込失敗時に以前のデータで発行させない。
- 元仮指示の数量・到着日・ロットと、現在の推奨／指示・到着日・ロットを比較表示する。データ識別と変更された入力区分も表示する。
- 商品・倉庫の組合せが変わった場合は再開照合を停止し、明細を黙って削除・追加しない。日付変更・「再開を終了」で新規計算へ戻る。
- 正式指示を仮指示として再開しない。旧版仮指示も再開せず、発行直前に参照元が最新か再確認する。元仮指示番号と比較結果を新しい発行履歴・帳票に残す。
- 受入条件：DBを閉じて開き直した再開、朝データでの数量保持と不足停止、修正後の正式発行、複数ロット保持、失敗時の旧データ排除、商品組合せ変更・旧版・正式履歴の拒否、競合と再検証、全テスト・固定日付デモ・Windows CI。

## 第5段階：履歴・取込原本のバックアップと復元

- SQLiteのバックアップAPIで一貫した履歴DBを取得し、保存済み帳票とマニフェストをZIPへまとめる。取込原本はDB内のJSON履歴に含む。既存ファイルへ上書きしない。
- 検証ではZIP内のパス・重複・ファイルサイズ・SHA-256、SQLite整合性・対応スキーマ・JSON・発行番号・改訂・原本ハッシュ・発行イベントとの一致を確認する。
- 復元は新規フォルダーへ限定し、既存DBや帳票を置換しない。検証失敗時は完成した復元先を作らない。
- 復元履歴は閲覧専用で開く。過去バックアップを本番DBへ巻き戻して発行番号を再使用しない。本番復帰・失われた出荷履歴との照合は業務側で決定する。
- 管理画面とCLIに作成・検証・新規復元を追加し、復元履歴の閲覧と通常データへの復帰を分ける。保存済みの確認状態を新たな現物確認として扱わない。
- 受入条件：作成・検証・別フォルダー復元、原本・改訂・帳票保持、閲覧専用ゲート、破損／不正パス／異形式／上書き拒否、失敗時の現行データ保持、全テスト・固定日付デモ・Windows CI。
